Most databases are built around one question: *does this record match exactly what I'm looking for?* That works great for finding a user by ID or orders from a specific date. It fails completely when you need to find *similar* things — documents that mean roughly the same thing as a query, images that look like another image, products that are conceptually like what a customer just described.

That's the problem **vector databases** solve. And once you understand them, the architecture of most modern AI features becomes obvious.

## What makes a vector database different

A traditional database stores structured data — strings, numbers, booleans — and looks things up with exact or range queries. `WHERE email = 'alice@example.com'` works because there's only one Alice.

A vector database stores **embeddings** — dense numerical arrays where position in space encodes meaning. Two pieces of text that mean similar things end up as vectors that are numerically close. Two that mean different things end up far apart.

Instead of matching a value exactly, you query by **similarity**: "find me the vectors nearest to this one." That operation — approximate nearest neighbor (ANN) search — is what a vector database is optimized to do, fast, at scale.

## How embeddings encode meaning

An embedding model converts any piece of text into a fixed-length array of numbers. The position of that array in high-dimensional space captures semantic meaning. Here's what that looks like in practice:

```python
import openai

client = openai.OpenAI()

def embed(text: str) -> list[float]:
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

# "I need help with my invoice" and "billing question" will be
# numerically close. "Cat videos" will be far away from both.
query_vec = embed("I need help with my invoice")
```

The vector itself is just numbers — you can't read it directly. But comparing two vectors with a distance metric (cosine similarity is the most common) tells you how semantically close the original texts were.

## What vector databases are actually used for

Vector databases show up in almost every AI-backed feature today:

- **RAG (retrieval-augmented generation)** — store document chunks as vectors; at query time, find the chunks closest to the user's question and inject them into the LLM prompt. This is far and away the most common use case. See [What Is RAG?](/blog/what-is-rag) for the full picture.
- **Semantic search** — return results that *mean* what the user asked, not just results that share the same keywords.
- **Recommendations** — "you liked this; here are similar ones" — represented as vector proximity.
- **Duplicate and near-duplicate detection** — flag content that is semantically equivalent even if the wording is different.
- **Memory for AI agents** — store past interactions as embeddings so an agent can surface relevant history without re-reading the entire log.

## How a vector database fits into a RAG pipeline

In a typical RAG system, the vector database is the retrieval layer — the piece that turns a user question into relevant context for the LLM.

| Stage | What happens | Vector DB involved? |
| --- | --- | --- |
| Indexing | Chunk documents, embed each chunk, store vectors | Yes — write |
| Retrieval | Embed the query, find nearest chunk vectors | Yes — read |
| Generation | Pass retrieved chunks to the LLM as context | No |

The LLM never touches the vector database directly — it only sees the text chunks that the database returned. The database's job is to find the right chunks, fast.

## Three things that separate a vector database from a plain list

You could store embeddings in an array and search it with a loop. For a few hundred vectors that works fine. At tens of thousands of documents (or millions of chunks), it breaks down:

1. **Speed** — scanning every vector linearly is slow. Vector databases use specialized indexes (HNSW, IVF) that find approximate nearest neighbors in a fraction of the time.
2. **Filtering** — real queries almost always have metadata constraints: "find similar docs, but only from this user's account, from the last 30 days." Vector databases handle combined similarity + metadata filtering efficiently; a plain array doesn't.
3. **Scale and persistence** — production systems need durable storage, concurrent reads, and the ability to add or delete vectors without rebuilding the entire index from scratch.

> Rule of thumb: if your embedding search is local and under a few thousand vectors, a library like `faiss` or even a sorted list is fine. Once you need persistence, metadata filtering, or multi-user scale, reach for a proper vector database.

## Choosing a category (without getting lost in product comparisons)

Vector database options broadly fall into three shapes:

- **Managed cloud services** — you store vectors via an API; the provider handles all infrastructure. Simple to start, easy to scale, no servers to run.
- **Self-hosted open-source databases** — you run the server, you control the data. More operational work, but more flexibility and no vendor dependency.
- **In-process libraries** — run entirely inside your application process, no separate server needed. Fast and simple for single-machine workloads; not horizontally scalable.

The right choice depends on your scale, latency requirements, existing infrastructure, and whether your team wants to operate a database. Most teams start with a managed service and optimize later if cost or control becomes an issue.

## Where vector databases alone aren't enough

Vector search returns the *nearest* vectors — but nearest isn't always *most useful*. A few limitations to know:

- **Keyword blindness** — embeddings can blur exact terms (product codes, error IDs, version numbers) across the vector space. A query for error `ERR-4021` may return results about errors in general rather than that specific code.
- **Top-k is not a guarantee** — if you retrieve the top 5 chunks but the right answer ranks 6th, it never makes it into the prompt. The model can't cite what it never received.
- **Individual chunks lack surrounding context** — vector search returns isolated chunks, not the documents they came from. A chunk can be semantically close to the query without actually answering it.

These aren't arguments against vector databases — they're arguments for not relying on vector search alone. Adding a reranking step, hybrid search (keyword + vector), and thoughtful chunking addresses most of this.
