If you've read anything about building AI applications, you've run into the phrase "store embeddings in a vector database." It shows up in every RAG tutorial, every semantic search guide, every recommendation engine walkthrough. But the term gets dropped without explanation, as if the reader obviously knows what a vector is and why it needs its own database.

This post fixes that.

## Why ordinary databases fall short

A traditional database is very good at exact matches. You ask for every user whose `country = 'US'` or every order where `status = 'pending'` and it returns them — fast, predictably, and exactly right.

That model breaks the moment the question becomes *fuzzy*. Ask a SQL database "find documents similar in meaning to this sentence" and it has nothing to offer. You could do a keyword search, but keyword search requires exact word overlap — it can't understand that "car" and "automobile" mean the same thing, or that a question phrased one way is semantically equivalent to content phrased another way.

Most of what AI applications need to look up is fuzzy. That's the problem vector databases exist to solve.

## What a vector actually is

Before a vector database makes sense, you need to understand what it stores.

An **embedding** is a list of numbers — a vector — that represents the meaning of a piece of text (or an image, audio clip, or anything else you've trained an embedding model on). The crucial property: content with similar meaning ends up with numerically similar vectors, even if the exact words are different.

```text
"The dog ran across the yard."  → [0.21, -0.54, 0.08, 0.73, ...]
"A canine sprinted through the garden." → [0.19, -0.51, 0.11, 0.70, ...]
"Revenue was up 12% this quarter." → [-0.34, 0.82, -0.61, 0.02, ...]
```

The first two sentences produce vectors that are close together. The third is far away. An embedding model — a specialized neural network — maps language into this geometric space, where closeness encodes meaning.

A real embedding might have hundreds or thousands of dimensions, but the principle is the same: **meaning becomes distance**.

## How a vector database works

A vector database is optimized for one thing that SQL databases have no efficient answer for: **nearest-neighbor search** — given a query vector, find the N stored vectors that are most similar to it.

The workflow in a RAG pipeline illustrates the full loop:

```text
Index time (once):
  document → embedding model → vector → stored in vector DB

Query time (per request):
  user question → embedding model → query vector
       → search vector DB for nearest neighbors
       → top-k chunks returned
       → chunks injected into LLM prompt
```

Searching millions of high-dimensional vectors by brute force would be too slow for production. Vector databases use **approximate nearest-neighbor (ANN) algorithms** — indexing structures that trade a small amount of accuracy for dramatically faster lookup. The approximation is close enough for retrieval purposes, and the speed gain makes it practical to run at scale.

Most also let you combine vector search with metadata filters — "find the nearest documents *and* restrict to `product = 'enterprise'` and `language = 'en'"`. That combination of semantic search with structured filtering is what makes them genuinely useful rather than academic.

## A quick comparison

| Feature | Traditional DB | Vector DB |
| --- | --- | --- |
| Best for | Exact lookups, structured data | Similarity search, embeddings |
| Query style | SQL / key-value | "Find nearest to this vector" |
| Scales to millions of vectors? | No (without extensions) | Yes |
| Metadata filtering | Yes | Yes (in most modern options) |
| Familiarity | High | Growing fast |

## Vector databases worth knowing

You don't need to memorize the landscape, but it's useful to know the names you'll encounter:

- **Pinecone** — managed cloud service, no infrastructure to run
- **Weaviate** — open source, supports hybrid search natively
- **Qdrant** — open source, strong filtering and on-disk storage support
- **Chroma** — lightweight, popular for local development and prototypes
- **Milvus** — open source, designed for large-scale deployments
- **pgvector** — a PostgreSQL extension; if you already run Postgres, you may not need a separate service at all

The right choice depends on your scale, whether you want managed infrastructure, and whether you're already invested in a particular stack. For a prototype, Chroma or pgvector gets you moving in minutes. For production at scale, Pinecone, Weaviate, or Qdrant are common choices.

> Rule of thumb: **start with what's already in your stack**. pgvector on your existing Postgres database handles a lot of real-world workloads without adding a new service to operate.

## When you actually need one

You need a vector database when you're doing semantic search and the data is too large to fit in memory or in a context window.

- Building a [RAG pipeline](/blog/what-is-rag) over thousands of documents
- Powering a search feature where users phrase queries in natural language
- Building a recommendation system based on content similarity
- Deduplicating documents or finding near-duplicates at scale

You probably *don't* need a dedicated vector database when:

- You have fewer than a few thousand embeddings — in-memory libraries like FAISS or simple arrays are fast enough
- You're prototyping — storing embeddings in a JSON file and doing a linear scan is fine to get started
- You already run Postgres — pgvector is a one-command install away

## The bottom line

A vector database is the missing link between the embedding model that converts text into numbers and the LLM that reads those numbers to answer questions. It handles the part that conventional databases can't: finding what's *similar*, at scale, fast enough to use in production.

Understanding this component is what separates teams that build demos from teams that build products. The retrieval step is where most RAG failures originate — and knowing how vector search actually works is the first step to knowing how to fix it when it breaks.
